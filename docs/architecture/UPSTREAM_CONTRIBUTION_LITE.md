# 外部プロジェクトへの貢献

## 窓口を選ぶ

READMEで不具合の連絡先を、CONTRIBUTINGや投稿テンプレートで変更の受け付け方を確認する。既に同じ議論があれば、新しく分かったことをそこへ足す。公開コードを改変・再配布できる範囲はライセンスで確かめる。脆弱性の連絡には指定のセキュリティ窓口を使う。

Issueでは、元の版で試した操作、期待した結果、実際に起きたことを届けられる。PRでは、作者が具体的な差分を読んで採否を決められる。小さく確かめられた修正なら先方の方針に沿って直接PRへ。大きな仕様変更なら先に方向を相談する。一件の報告は一つの適切な窓口で足りる。

## 修正を届ける前に

- AI利用・開示・人間によるレビューの条件を提出先で確認する。投稿者が説明できる範囲に差分を絞り、誰が何を確認したかを正確に書く。署名や同意の意味は本人に伝える。
- 修正版を元の操作で試す。実機でしか分からないことがあり、その機器が手元にあるなら、普段の画面から試せるところまで用意する。端末間同期なら、接続コードの表示、登録、データの到着を別々に観察できる。
- 本文には元の症状、変更理由、試した条件と結果、残る疑問を先方の用語で書く。部分修正は効いた範囲をタイトルにする。再現や判断に効く情報を残し、端末の秘密や関係のないログは除く。
- ローカルで試すことと、本人の名義で外部に提出することは、会話で任された範囲に合わせる。「修正案を送るのはどう？」なら、まずその道を選ぶ意味を答える。

## 提出したあと

追加の実測は最初の症状を残して本文にまとめる。既にレビューされた前提が変わったら、その会話にも短く返す。別の製品側で止まった場合、観測した地点を伝え、その先の調査や採用の時期は先方が選べるようにする。
